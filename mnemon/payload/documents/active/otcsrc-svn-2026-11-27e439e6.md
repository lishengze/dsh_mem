# otcsrc SVN 改动审阅与提交基线（2026-11 实战沉淀）

适用：在工作副本 `otc_src`（容器内 `/mnt/work/otc_src/otcsrc`）审阅未提交改动、给出"改得对不对 / 该不该提"的判定时，先按本文核对，避免重复踩坑。

## 1. 环境与命令基线

- **locale 必须显式设**：容器默认 `LC_ALL=POSIX`，`svn status` 遇到中文文件名会直接报 `E000022`。所有 svn 命令前置 `LC_ALL=zh_CN.utf8`。
- 取服务端版本：`svn status -u` 末行 `Status against revision: rNNNNN`。
- 查他人并行提交：`svn log -r <起>:<止> -q`，再用 `svn diff -c <rev>` 定点看。
- 判定"本地 M 是否会被覆盖"：`svn status -u` 输出中带 `*` 的文件 = 服务端有更新；需与实际 M 列表求交集。
- 已知噪声：`?` 列表中常有 `compile.log`、`bin/bin64_windows/*.dll` 等构建产物，属正常，不必处理。

## 3. 已确认的缺陷模式（可直接复用）

### 3.1 分页 offset off-by-one（高频）
- `m_nOffset` 语义应为"跳过条数 / 起始下标"，`m_PerQryFundDelay.m_nOffset` 与 `m_QryParam.m_nOffset` 均按此用（411535 L291、410567 L474 是正确用法：`nStartIdx = m_nOffset`、`nMatchCount <= m_nOffset` 跳过）。
- 错误用法：把 `nOffset` 当"窗口末端下标"、循环却从 0 起（411834 L444）→ 默认值 1 时**多返回 1 条**。
- 默认值设 1 会"永远跳过第 1 条"，客户只有 1 条匹配记录时直接查空。全仓曾残留约 10 处默认 `m_nOffset = 1`，改 1→0 时须逐个看是"真实缺陷"还是"仅打印、行为中性"。

### 3.2 411830（基金投顾待确认数据明细查询）qryflag 契约
- 契约：`qryflag char(1)` **非必填、默认 '0'**，合法取值 {'0','1'}。
- **旧系统确实校验**：`jzjy_trunk` 下 `fundtran.cpp` 的 411830 handler（`Cperiphery::perofStrategyQryOftrans`）显式判断 `cQryflag` 非 '0'/'1' 即 `BusRaiseException(-411538020, "qryflag入参值有误")`。因此"旧系统未显式校验、故新框架取消校验"的说法是错的，取消非法值校验属**相对旧系统的契约回归**。
- 正确做法（方案 A 的双段）：① 入参为空（`TryGetValue` 取到 `' '`/`'\0'`）时**不要覆盖**已设的默认 `'0'`；② 非空但非法（如 `'X'`）时**必须报错** `-411830020`。
- 新框架错误码家族：`-411830020` qryflag 非法、`-411830030` 主账户非普通账户、`-411830040` 子账户不存在（与旧系统 010/020/030 顺延风格一致，非笔误）。
- 佐证一致性：mock `req_70411830.xml` TC-13 期望 `error code=411830020`；`411830_参数对比.md` 亦记"新旧均校验"。若取消校验，TC-13 必然失败。
- 查询标志类字段在旧 `BusTag.h` 中统一叫 `cQryflag`，语义注释多为"查询类型 / 0 当前 1 历史"，跨接口不可想当然照搬语义。

### 3.3 411535（基金延迟订单查询）
- 表不存在时"静默成功返回空"是错误的：应显式抛 `411531040 delay_fund_table_not_found`（与家族 010/020/030 顺延）。
- `cursor.add_condition` 字段名必须用库表**真实列名**：`cust_id` / `fund_id`（带下划线），而非入参字段名 `custid`/`fundid`。

### 3.4 Kafka 转发时机
- 内存库记录 → Kafka 转发走 `base_processor.h` 的 `ForwardRecordToKafka(szTable, szOp, tRecord, szFuncId)`，封装见 `public/comm/kafka_record_forwarder.h`。
- **必须在事务 Commit 成功后转发**（避免回滚数据被外部看到），记录对象需提到事务作用域之外。样本：`seriinfo_set_processor.cpp`（`otc_seriesinfo`）、`limitctrl_set_processor.cpp`（`otc_oflimitctrl`）。
- 新增 include 若指向仓库内头文件，该头文件必须已在版本控制内，否则他人 update 后整模块编译失败。

## 4. 提交前四查（缺一不可）

1. **新增 include 已入库**：所有新增 `#include` 的仓库内头文件 `svn status` 不得为 `?`，必要时 `svn add`。
2. **二进制/编译产物不入库**：`A bin/bin64_linux` 这类目录（曾误入库 11 个 .so、约 51MB，含 42MB `libjstp_memdb.so`）一律 `svn revert`；revert 只改版本控制状态，本地文件保留。
3. **与服务端交叉核对**：`svn status -u`，确认 M 文件未被他人先改，避免提交冲突或覆盖。
4. **update 到服务端 HEAD 后重新编译回归**：定向 `make` 到 `Built target`，不 `install`、不动部署库。

分批提交建议：按主题拆（Kafka 转发 / offset 修复 / 411535 / 411830 各一批），避免"一半对一半越界"的改动混入同一提交。

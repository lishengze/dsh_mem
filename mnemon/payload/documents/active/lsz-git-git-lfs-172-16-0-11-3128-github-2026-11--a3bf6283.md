# 本机 git / git-lfs 走代理访问 GitHub 的完整方案（2026-11-26）

适用环境：lsz 开发机（Ubuntu，`/home/lsz/code` 下 14 个 GitHub 仓库，remote 全为 `git@github.com:lishengze/*`）。
网络约束：直连 `github.com:22` 与 `github.com:443` **均不通**，唯一可达出口是 HTTP 代理 `172.16.0.11:3128`。

## 1. 核心结论：两套通道，缺一不可

| 需求 | 走什么协议 | 靠什么配置 |
|---|---|---|
| git 传输（fetch / push 的对象与引用） | SSH | `~/.ssh/config`：Host `github.com` → `ssh.github.com:443` + `ProxyCommand corkscrew` |
| git-lfs（push 时必调的 `locks/verify`、LFS 对象上传） | **HTTPS** | `git config --global http.proxy http://172.16.0.11:3128` |

**关键认知：git-lfs 完全不读 `~/.ssh/config`。** 它自己向 `https://lfs.github.com/<owner>/<repo>/locks/verify` 发 HTTPS 请求
（`lfs.locksverify` 默认 true，所以**每次 push 都会调**）。因此 SSH 隧道配好 ≠ push 能过。

## 2. 代理的行为边界（实测）

| 测试 | 结果 |
|---|---|
| 直连 `github.com:22` | 不通 |
| 直连 `github.com:443` | 不通 |
| `172.16.0.11:3128` 本身 | 可达 |
| `corkscrew` → proxy → `github.com:22` | ❌ `kex_exchange_identification: Connection closed by remote host`（**代理拒绝 CONNECT 22**） |
| `corkscrew` → proxy → `ssh.github.com:443` | ✅ `Hi lishengze! You've successfully authenticated` |
| HTTPS 凭据路线（`https://github.com/...`） | ❌ 无凭据：`credential.helper=manager-core` 但组件未安装，无 `~/.git-credentials`，无 `gh` |

⇒ 选 GitHub 官方 **SSH over 443**，比切 HTTPS 省掉 token 配置。
本机可用工具：有 `corkscrew`、`nc`（OpenBSD netcat，`-X/-x` 可用）；**无** `ncat` / `connect` / `socat`。

## 3. 最终落地配置

### 3.1 `~/.ssh/config`（此前不存在，新建，权限 600）

```sshconfig
Host github.com
    HostName ssh.github.com
    Port 443
    User git
    ProxyCommand corkscrew 172.16.0.11 3128 %h %p
    StrictHostKeyChecking accept-new
    ConnectTimeout 15
    ServerAliveInterval 30
    ServerAliveCountMax 3

Host ssh.github.com
    HostName ssh.github.com
    Port 443
    User git
    ProxyCommand corkscrew 172.16.0.11 3128 %h %p
    StrictHostKeyChecking accept-new
    ConnectTimeout 15
    ServerAliveInterval 30
    ServerAliveCountMax 3
```

**为什么用 `~/.ssh/config` 而不是 `git config --global`：**

| 方案 | 问题 |
|---|---|
| `git config --global core.sshCommand` | 对所有 SSH 远端（gitlab/内网 git）强套 corkscrew，会打断本可直连的主机 |
| `git config --global url.insteadOf` | 只改地址，拿不到 ProxyCommand，还得再配第二个键 |
| **`~/.ssh/config`（采用）** | 按 host 精确生效；`git@github.com:xxx` URL 原样不变，连接层自动改写；`ssh -T git@github.com` 也直接可用 |

先期曾在单仓 `otc_src` 写过仓库级 `core.sshCommand` + `url.insteadOf`，改全局后**已撤销**，避免同一件事两处配置、改一处忘另一处。

### 3.2 git / git-lfs 的 HTTP 代理

```bash
git config --global http.proxy http://172.16.0.11:3128
```
（原 `~/.gitconfig` 备份为 `~/.gitconfig.bak.20261126`）
git-lfs 会继承 git 的 `http.proxy`——**实测清空所有 `*_PROXY` 环境变量后仍能连通**，说明配置本身足够，不依赖会话环境。

## 4. 真正的元凶：`HTTP_PROXY` 地址笔误

环境里 `HTTP_PROXY=http://127.16.0.11:3128`（应为 **172**.16.0.11），`HTTPS_PROXY` 是对的。
`127.16.0.11` 属回环段 → `dial tcp 127.16.0.11:3128: connect: connection refused`，即用户报错的原文：

```
Post "https://lfs.github.com/lishengze/server_5/locks/verify":
proxyconnect tcp: dial tcp 127.16.0.11:3128: connect: connection refused
```

该变量**不在** `~/.bashrc` / `~/.profile` / `/etc/environment` / `/etc/profile.d/*` 中，是 IDE/桌面会话注入的，脚本层改不掉；改全局 `http.proxy` 后它对 git/lfs 不再有影响。

## 5. 验证矩阵（可复用为回归脚本思路）

| 验证 | 期望 |
|---|---|
| `ssh -G github.com` | `hostname ssh.github.com` / `port 443` / `proxycommand corkscrew …` |
| 裸 `ssh -T git@github.com` | `Hi lishengze! You've successfully authenticated` |
| 未做仓库级配置的仓库 `git ls-remote`（gt_trunk→server_5 等） | 正常列出分支 |
| 错误代理 `127.16.0.11` | 精确复现 `connection refused`（证明诊断正确） |
| 无任何代理 | `dial tcp 20.205.243.168:443: i/o timeout`（证明测试有效） |
| 正确代理 `172.16.0.11:3128` | `git lfs locks` 正常返回 |
| 清空所有 `*_PROXY` 后仅靠全局 `http.proxy` | `git lfs locks` 仍正常 ✅ |
| `git push --dry-run origin trunk:trunk`（走真实 LFS 校验，不动远端） | 打印 refspec 更新，exit 0 |

**排查方法论**：先用 `--dry-run` 走完 LFS 校验链路再真推；对每种失败做「反证实验」（错误代理必失败 / 无代理必超时），确认修复点唯一。

- `origin/master` 已严重分叉：本地 `master` 落后 41 / 领先 960，远端 `master` 疑似废弃分支（本仓实际以 `dev` 为主线）。未动，待用户决定推送或删除。

## 7. 可选兜底

1. `git config --global lfs.locksverify false`：彻底绕开 `locks/verify`。本机 14 个仓库 LFS 跟踪文件数全为 0（无 `.gitattributes` LFS 规则），关闭无副作用。
2. 修正 `HTTP_PROXY` 为 `http://172.16.0.11:3128`：需在注入它的 IDE/桌面启动配置里改，脚本层无法覆盖。
3. 换网络想直连时临时绕过：`ssh -F /dev/null -T git@github.com`、`git -c core.sshCommand='ssh -F /dev/null' fetch`。

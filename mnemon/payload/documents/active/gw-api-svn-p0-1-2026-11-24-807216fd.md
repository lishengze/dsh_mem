## 1. 用户的三条裁决逻辑（最高口径，优先于任何助手建议）

| # | 逻辑 | 理由 |
|:-:|---|---|
| ① | **性能优化相关的日志注释一律保留** | 日志字符串的构造本身耗时：即使降到 `kDebugLog`，`std::string log_info = "..."`、`ostringstream`/`boost::format` 格式化**仍会执行**。因此「上游把日志降级」不等于「本地注释可放弃」 |
| ② | **两处不进 SVN，以补丁形式留在工作副本**：UTE 直连段去 `/* */`；`Connect()` 早返回 `kSuccess` + 补齐 `user_/password_/guomi_password_/user_type_`（合称 **P0-1**） | 尚未与同事确认，不能提交 |
| ③ | **其余一律以上游为准** | 上游的空间路由（按 `market_id` 分流 UTE / AGW→UTE）、判定逻辑重构、防御性错误日志 |

这是对早期「冲突文件全部取远端 + 本地改动补丁重放」口径（见文档 `a7e662dd-488d-462b-9523-ba4004d5ebd7`）的**细化**：仅 P0-1 走补丁化，其余就地取上游，日志注释就地保留而不外置成补丁。
另一份冲突处置先例可参照 `64592da6-cecb-4bb5-ab4a-5ce1124761b0`（NewAPI r21，「接口跟上游、能力保本地」）。

## 2. 逐块处置的两条实施要点

1. **融合形态**：取上游代码结构（含 `GetMarketID` 分流分支），把其中的日志块替换回本地注释态，而不是整块保留本地或整块取上游。
2. **注释粒度**：必须注释掉整个 `if (client_handler_ != nullptr) { std::string log_info…; OnLog }` 块。只注释 `OnLog` 一行等于没优化——字符串构造依旧发生。唯一例外：no_boost #3 的 `kErrorLog` 兜底日志原样保留（非热路径 + 排障线索）。

## 3. P0-1 补丁化流程（照 `sendlogin` 先例）

先例文件：`svn_work/05-代码同步与工程/sendlogin_restore_apply_20261122.patch`（标准 `a/ b/` 前缀可直接 `patch -p1`）、
`sendlogin_restore_20261113.patch`（旧格式，仅存档）、`sendlogin_README.md`（含「剥离后 TCP 无法登录，0/13 → 恢复后 13/13」的实测后果）。

要点：**平时工作副本带 P0-1 → SVN 提交前剥离成上游原样 → 提交后立即恢复**。
状态判据可用标记串计数：`grep -c "不可注释掉"` / `grep -c "UTE 直连模式下已发起连接"`，
平时各 1，提交前 0，提交后回到 1。

## 4. 解决后的验证清单（摘）

除常规「无冲突标记 / `svn status` 不再是 `C` / 可编译 / SHM 功能回归沪深各 5/5」外，本次新增三条：

- P0-1 仍在（上述标记串各 1）；
- 上游功能已进（`GetMarketID(msg_type` ≥1，两树各有）；
- **日志注释粒度正确**（冲突块内不得残留裸 `std::string log_info`，`kErrorLog` 兜底分支除外）；
- P0-1 剥离/恢复状态与所处阶段一致。

## 5. 附带事实与踩坑

- 冲突标记曾被一次 git 提交带入库（坏提交 `62c52ec61`），故 git 侧需单独一条「修复冲突标记」提交。
- 兄弟仓 `gt_svn`(svn_remote) / `gt_sit`(svn_sit) 两树同文件存在但**冲突标记 0**；两仓源码基线不同，不默认照搬，先各自确认版本。
- 会话异常中断后的核查套路：`git status` 里出现「内容零 diff 却是 `M`」基本是**权限位漂移**（index 100755 / 工作区 644），`git diff` 显示 0 行差异即可确认，`chmod 755` 还原即可，勿按内容改动处理。
- 另一类中断损坏：命令块里 `bash -c '...` 的**结尾单引号被吞**，`bash -n` 会报 `unterminated quoted string`；修复前先用 `bash -n` 校验（见 `task/task_svn/task_svn.txt` L489 起的 docker+svn commit 块）。

# policy_id 位置变更对共享内存通道的影响（2026-11-20）

**一句话**：FTE 侧 `policy_id` 由「`TradeOrderInfo` 内部属性」改成「基线宏 + 扩展字段」，`TradeOrderReqLayout` 随之 **108 → 106**；但共享内存通道的**结构不用改、业务体下限绝不能跟着降到 106**。本次只改字节契约自检脚本，通道代码零改动。

产出：`svn_work/134_policy_id位置变更对共享内存通道的影响_20261120.md`（7 章 / 248 行）、`work_log/20261119.md`；提交 `376848f4b` 已推送，三仓 0 0。前序背景见 [GT 三仓 policy_id 贯通方案](9edbc756-0ad0-4081-81e8-475f7983f83e)、[FTE 方案Q 提交清单](85c276bd-e6a0-4cd2-956a-139ae6487dfa)、[test/share_test 升级](98683cb9-f567-47ff-b952-2ebc8a769a36)；本文只记**布局语义变更**带来的新知识。

## 1. 改动前后（字节契约）

| 结构/概念 | 改动前 | 改动后 |
|---|--:|--:|
| 基线证券字段 | 内联在 `TradeOrderInfo` | 抽为宏 `BASE_TRADE_ORDER_SEC_INFO_FIELDS`（36B） |
| `TradeOrderInfoLayout` | 不存在 | **新增**，仅基线，**36** |
| `TradeOrderInfo` | 38（基线 + policy_id） | 38（基线 + **扩展字段** policy_id） |
| `TradeOrderReqLayout` | **108**（含 policy_id） | **106**（70+36，**不含** policy_id）＝内部准入下限 |
| `TradeOrderReq` | 116 | 116（`reserved` 改按完整业务体推导，不随 Layout 变小） |
| SHM `share_common::TradeOrderReq` / 业务体 | 124 结构 / 116 业务体 | 不变：124 / 116，仍与内部 `TradeOrderReq` 逐字节同构 |

语义目的：让**只带 106 业务体的老客户端重新可准入**——此前会被 108 门槛判 `too short` 而整条丢弃。另新增 **4 条 `static_assert`** 固化新契约。

## 2. 通道要不要改：结构不改，下限不能改

- **结构不用改**：SHM `TradeOrderInfo` 仍含 `policy_id`@36 → 38B；结构 124、业务体 116，与内部 116 同构 → 仍走 `kPass` 零拷贝。
- **下限绝不能对齐成 106**，三条理由：
  1. SHM 是**定长元素队列**（元素步长 124），老 114B 结构挂不上同一队列；兼容靠**头文件版本一致**，不靠放宽长度；
  2. 降到 106 后，106~107 的非法 body 会被补零按 `kReuse` 接受 → `policy_id` **静默变 0**，比拒单更难查；
  3. 头文件既有断言 `kShmOrderReqBodyLen − kShmOrderReqBodyMin == 8` 天然阻止误改（116−106=10≠8 → **编译期失败**）。
- 结论句式：内部下限 106 与通道下限 108 是**两个不同概念**，不可"对齐"。

## 3. 实际代码改动（仅自检脚本）

`DYS-FRAMEWORK/fte/test_all/check_wire_abi.sh`：

| 改动 | 原因 |
|---|---|
| `EXP_REQ_LAYOUT` 108 → **106** | 不改则自检 `fail=1`（**实测复现**：`sizeof(TradeOrderReqLayout)=106 (期望 108)`） |
| 新增 `TradeOrderInfoLayout == 36` | 固定基线视图 |
| 新增 `Layout + policy_id == 完整业务体` | 固定"严格前缀"关系 |
| 新增 `kShmOrderReqBodyMin == 108` | 明确区分通道下限与内部下限，防后人"对齐"误改 |

断言数 **25 → 28**，全部 PASS。

## 5. 两类易误判的环境陷阱（与本次改动无关，但会伪装成回归）

| # | 现象 | 真因 | 判别 |
|:-:|---|---|---|
| 1 | 重建后委托全拒，ute 日志里**完全没有** `dse_ute` | `compile_fte_all.sh` 探测 `libabf_te.so` 的路径不含 `work_atp/cmake/biz_framework/lib` → 自动降级为 **NO_DSE 版 ute** → 基金数据缺失 → `DealTradeOrderReq Check Fail` 拒单 | 日志无 `dse_ute` ⇒ 编成了 NO_DSE；重建时**显式** `FTE_WITH_DSE=ON BUILD_DSE=OFF`（只重建 ute，不重建 dse 本体） |
| 2 | `logon_feature_code not match <A> <B>` | 同一资金账号已被先前会话（另一 `strategy_key`）登录占用，FTE 拒绝跨策略下单 | 重启 FTE 清空登录态；用例账号要与环境里真实存在的基金账号一致（本次临时改用 `1000000000000001/0001`，事后已还原 `test/share_test/test_data.json`） |

另一条通用判别：**拒单文本是 `Check Fail`/`logon mismatch` 而不是 `too short` ⇒ 与长度、布局无关**，不要往字节契约上查。

# API 报文 ID 字段语义与回填关系（2026-11-05）

仓库正文（权威版本）：`study/knowledge_base_system/20_API报文ID字段语义与回填关系.md`，同批更新 `08_API模块.md`、`MEMORY.md` 索引；提交 `cff704fca`（gt_trunk trunk，已推送，上游 0/0）。本记录是检索层摘要，冲突以仓库正文与代码为准。

## 1. 结论速查（可直接对外答复）

| 问题 | 结论 |
|---|---|
| 撤单报文要填哪个号 | 原委托响应里的 **`client_order_no`**（内部 `clordno`）→ 撤单请求 `orig_cli_ord_no`。原委托自身的 `orig_cli_ord_no` 恒为 0；`cl_ord_id`、`exec_id` 都不是委托号 |
| 撤单响应里的号是谁的 | `client_seq_id` / `client_order_no` / `cl_ord_id` 都是**撤单这笔新委托**的新号（实测 `1700000021` / `552000000L` vs 原单 `1700000019` / `552000000J`）；`orig_cli_ord_no` 才回指原委托 |
| `order_id` 有值代表撤单已受理吗 | **不代表**。撤单被交易所受理/拒绝的判据看 `exec_type` / `order_status` / `reject_reason_code`（如 `order_status=8` + `50046`「原单已全部成交」） |
| 一笔委托多次成交 | `exec_id` 是**成交编号**，一笔委托多次成交有多个值，与委托号不同域 |

## 2. 三层命名映射（口头/文档沟通必须给全）

| 层 | 载体 | 委托号字段 |
|---|---|---|
| 外部报文 / 客户端 API | `AgwMsg*`（`gw/external/codec/messages_agw_external.h`） | `client_order_no` / `cl_ord_id` / `order_id` / `orig_cli_ord_no` |
| FTE 内部回报结构 | `OrdERInfo`（`fte/include/message/gw_external_message.h:236`） | `clordno` / `cl_ord_id` / `order_id` / `orig_clordno` |
| 扁平协议头 | `gw_head.h`（`TradeOrderER:903`、`CancelOrderReq:826`） | 同上按结构展开 |

报文映射：`2003 kPktOrderAns → kAgwMsgOrderStatusAck(290001)`、`2004 kPktCancelOrderAns → 290001`、`2005 kPktOrderMatch → kAgwMsgCashAuctionTradeER(210115)`。

## 3. 类继承链（决定哪些字段存在）

- `AgwMsgOrderReport`（24 字段基类）→ `AgwMsgOrderStatusAck`（+ 冻结金额/费用/拒绝码/ord_type/time_in_force/position_effect 等）。
- `AgwMsgOrderReport` → `AgwMsgTradeExecutionReport`（`exec_id`/`last_px`/`last_qty`/`total_value_traded`/`fee`）→ `AgwMsgTradeExecutionReportSeqNum`（+ `client_seq_id`）→ `AgwMsgCashAuctionTradeER`（+ `cash_margin` 信用标识）。
- 即：**委托响应/撤单响应本身没有 `exec_id`；成交回报的 `client_seq_id` 来自中间层 `...SeqNum`**。

## 4. FTE 不回填、由客户端 API 本地缓存补的字段

`ord_type` / `time_in_force` 等在 `UTEClientHandlerImpl::fill_orderstatusack_by_origorder` / `fill_orderstatusack_by_origcancelorder`（`api/src/ute_client_handler_impl.cpp:880` / `:1360` / `:1978`）里是**从本地订单缓存按原单补齐**（同名 `use_fill_*` 包装见 `api/include/agw/ute_client_handler_impl.h:258-283`）。自研客户端若不维护这份缓存，这两字段会为空 → 应按 `client_order_no` 自行保存。

## 5. 待证/取证纪律（复用）

1. **XML 描述与实现冲突时以实现为准**：`orig_cli_ord_no` 文档写「客户合同号/ClOrdID」，实现与实测填的是客户**订单**号（实测 `orig_cli_ord_no=1700000019` = 原单 `client_order_no`，≠ `cl_ord_id=552000000J`）。
2. 任何「字段语义」答复固定走 **定义 → 填充 → 解析 → 实测** 四步，并写「谁生成/何时回填」；只写含义会被反复追问。
3. 与 `6cebe0bd-7ebc-44ee-8c94-55551983a76b`（mock_client 撤单必须用真实委托号 `$last_order_sys_no`，固定 `"0"` 在 SH/SZ 均超时）互为印证：撤单链路确实按原委托号查表。
4. 相关文档：`e29e0f3b-3ebd-4dc9-8332-23488b558f12`（同两个 `ute_client_handler_impl` 文件的 ETF 发送链路三层缺失）。

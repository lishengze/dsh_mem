## 2. 每个业务的实质问题（都不是"缺数据"那么简单）

- **412232**：实现里**根本没有** `testcase_num` 造数据逻辑（`req_70412232.xml` 却带该字段）。本轮新增完整 `InsertTestCase*` 函数族，覆盖 13 个案例的数据条件：客户不存在 / 客户状态异常 / 机构客户（`custprop='4'`）/ 密码错误 / 账户状态异常 / 账户不存在 / 账户不属于该客户。
- **410567**：三个叠加问题——
  1. `req_70410567.xml` **完全没传 `testcase_num`**，所以处理器里那套 `switch` 造数据是**死代码**，从未执行；
  2. `TruncateAllTables()` 会清空 `acc_customer_info`/`acc_fund_account` 等**共享表**，是跨业务事故源；
  3. 造数据与用例**错配**：代码造客户 3 与 `'*'` 状态账户，而用例实际查客户 6。
- **411828**：造数据的转出账户是 `…02`，用例传 `…08`（长期错配，非本轮引入）。修正后仍崩溃，见第 4 节。
- 通用坑：代码里 `InsertTestCaseN` 的 N 与文档 TC 编号**语义不一致**（如代码 case 2 是"客户代码为空"），核对时必须看实现而非编号。

## 3. 可复用规范（落地四要素之外的补充）

1. **号段**：每个业务独立前缀，如 412232→`41223200000000NN`、410567→`41056700000000NN`；不再复用 `custid 1~6` 这类公共号码。
2. **入口**：`ParseParameters()`/`GetUserParam()` 中按 `testcase_num` 调造数据函数，**先于业务校验**执行（否则状态类错误码被前置校验抢先返回）。
3. **插入方式**：upsert（先按主键 `GetRecordPtr` 查、存在则 `Delete` 再 `Insert`）。内存库跨轮次持久化，裸 `Insert` 撞主键会静默失败，表现为"代码已改但结果不变"。
4. **禁清共享表**：`acc_customer_info`/`acc_fund_account`/`acc_vip_customers`/`acc_ofstrategysign`；`sys_config` 仅保证存在（查询类）或幂等重建（交易类），满足 Atom 层 `InitSysconfigBase()`。
5. **预期以实现为准**：断言前先确认真实契约，不要照文档 SQL 想象。修正的是用例，不是代码。

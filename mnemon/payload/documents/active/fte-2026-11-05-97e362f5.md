## 1. 多代码库切换

- 新增 `repos.py` 仓库注册表，每个仓库声明 `code_dir`（源码树）/ `work_root`（测试根）/ `build` / `deploy`；
  `config.json` 增加 `repos` 与 `active_repo`。
- `POST /api/repo` 切换 **服务端状态**：所有接口自动跟随，前端不必逐接口传 `repo`。
  这是本次的关键设计取舍——把「当前仓库」放在服务端单一状态点，避免前端几十处请求各带参数导致漂移。
- `actions.py` 支持三种构建方式：`script`（gt_trunk / gt_svn 用 `compile.sh -r`）、
  `cmake_make`（gt_sit：`cmake -S <src> -B <build>` + `make -C <build> -j10`）、`copy`（仅部署已有产物到 `run/`）。
- `Job` 增加 `repo` 字段，任务可追溯；切换后编译/部署/启动/功能/性能与代码浏览树全部作用于该仓库。

- 左栏目录树（跳过 `build*/.git/.svn/CMakeFiles` 等噪声目录，单目录 2000 条上限），右栏带行号源码。

## 3. 过程中修掉的三个真问题（可复用教训）

1. **构建脚本基准：源码树 vs 测试根。** 原实现从 `work_root` 找 `compile_fte_all.sh`，
   实际脚本在源码树 → 三个仓库的 build 全部报「找不到编译脚本」。
   修法：`_build_or_deploy` 的步骤 `cwd` 改用 `code_dir`，只有部署产物目标才落 `work_root`。
   教训：**同一动作里「脚本从哪来」和「产物往哪去」是两个不同的根**，不要共用一个 base。
2. **`_wrap_plane` 只映射 `argv[1]`。** 宿主机直连时把命令 `docker exec` 进容器，
   只把 `argv[1]` 的宿主路径转成容器路径；`cmake -S A -B B` 的多段路径漏映射，
   容器内报 `CMake Error: The source directory "/home/lsz/code/work/gt_sit_src/.../" does not exist`。
   修法：注入 `-e CODE_ROOT`，命令改用 `$CODE_ROOT/$WORK_ROOT` 由容器内展开，并对全部参数做路径映射。
   教训：**跨执行面（宿主↔容器）映射路径时，凡是"命令串里有几个路径"就要映射几个**，
   单点映射在只有单参数的脚本上恰好能过，一到 cmake 这种多路径工具就暴露。
3. **改完代码必须重启 console。** 服务进程持有旧模块，不重启则改动不生效
   （现象：明明改了 `actions.py`，接口仍报旧的「找不到构建源目录」）。这会把「代码写错」误判成「逻辑错」。

另：容器 `otc` 未运行时所有动作会退化成宿主机执行，并报与代码无关的 `libodbc.so.2` 缺失——
`_wrap_plane` 现已在「容器存在但 stopped」时快速失败并提示 `docker start otc`，不再假装执行。

## 5. 验收手法（可直接复用）

- 服务端状态切换用「切走 → 查 → 切回」三步断言（切到 gt_sit 后 `/api/health` 的 work_root 应变成 gt_test_sit，再切回 gt_trunk）。
- 长任务（cmake 编译 ~9 分钟）一律走后台 job + 轮询 `/api/jobs/<id>`，不要同步阻塞请求；
  单次脚本等待窗口设成与任务时长同量级，否则会误报 `URLError: Connection refused` / timeout。
- 门禁状态（必须先成功编译才能部署）在重启后清零，属预期行为，测部署前要先跑一次编译。

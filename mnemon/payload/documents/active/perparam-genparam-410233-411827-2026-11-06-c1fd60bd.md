# 旧系统公共入参宏口径核查：PERPARAM vs GENPARAM，及 410233 / 411827 的文档与代码缺口（2026-11-06）

> 工作副本：`/home/lsz/code/work/otc_src`；旧系统参考库：`/home/lsz/code/work/jzjy_trunk`。
> 本文记录一次针对「新框架公共入参是否对齐老系统」的核查结论，含一处**参数对比文档自身写错**的纠正。
> 相关文档：`1ccf9f31-6114-4272-b2a8-bd1656c2f2db`（411828 SIGSEGV：GetPerGeneralParam 只能在 ParseParameters() 内调用）、`5fd12a90-6def-44fc-b708-443d1642bc8b`（参数对比「错误信息统计」口径）。

## 1. 结论速览

| 业务 | 旧系统实际用的宏 | 参数对比文档写法 | 代码是否有缺口 |
|---|---|---|---|
| 410233 `perQryCustFundAsset_Retained` | **`GETVALUE_PERPARAM`**（无前缀） | ❌ 误写成 `GETVALUE_GENPARAM`（8 个 g_ 字段） | 无（trdpwd/custid 同名可读，且有密码比对） |
| 411827 `ofStrategyQryFundidJJTG` | **`GETVALUE_GENPARAM`**（g_ 前缀） | ✅ 正确 | **有**：无柜员权限校验，公共入参解析后完全未被业务读取 |

一句话：**410233 是「文档错、代码对」；411827 是「文档对、代码有缺口」。**

## 2. 两个宏的事实（旧系统 `jzjy_trunk/lbmdll/GeneralBus/GeneralBus.h`）

| 宏 | 行号 | 字段命名 | 适用接口族 |
|---|---|---|---|
| `GETVALUE_PERPARAM` | 1112 | **无前缀**：`funcid`/`custid`/`custorgid`/`trdpwd`/`netaddr`/`orgid`/`operway`/`ext`/`operwayext`/`userinfo` | 4 开头**外围接口**（periphery） |
| `GETVALUE_GENPARAM` | 1181 | **带 g_ 前缀**：`g_serverid`/`g_funcid`/`g_operid`/`g_operpwd`/`g_operway`/`g_stationaddr`/`g_userinfo`/`g_operwayext` | 7 开头**集中营运接口** |

结构体差异（同库）：
- `tagGeneralParam`（`lbm_comm/Business/include/GeneralBusTag.h:66`）：`nServerid/nFuncid/nOperid/sOperpwd/cOperway/sOperwayExt/sStationaddr/sTrdpwd/sTerminalInfo/sUserinfo`
- `tagPerGeneralParam`（同库 `:3395`）：`nCustid/cCustprop/sCustOrgid/sTrdpwd/sNetaddr/sOrgid/cOperway/cExt/nFuncid/sTerminalInfo/sNetaddr_ext/sOperwayExt/sUserinfo`

新框架 `CQueryBase::GetGeneralParam()` **只按无前缀名字解析**，仅 `funcid` 为空时回退读 `g_funcid`。若调用方按 `g_operid` 上送，新框架收不到。所谓「g_ 兜底」即给这些字段补「无前缀取不到再读 g_ 版本」的逻辑。

## 3. 410233：文档写错了旧宏（不涉及代码缺陷）

证据链（旧系统）：
```
lbmdll/lbm_periphery/LBMExport.cpp:20404  perQryCustFundAsset_Retained(char *pCA)
                                   :20413  GETVALUE_PERPARAM        ← 无前缀宏
lbmdll/lbm_periphery/stocktran_Retained.cpp:246  Cperiphery::perQryCustFundAsset_Retained
                                            :263  CheckQryTrdpwd2(..., BusParam.PerParam, ...)
                                            :270  GF_GetFundinfo(..., BusParam.PerParam.sCustOrgid, ...)
```

因此 `study/410233_*/410233_参数对比.md` 的「1.1 旧系统公共参数（`GETVALUE_GENPARAM` 宏）」小节整张表都错——8 个 g_ 字段一个都不该出现，应改为 PERPARAM 口径的 10 个无前缀字段。

功能无问题：`PerParam.trdpwd` → 新框架 `GetValue("trdpwd", ...)` **同名可读**，且业务内有密码比对（410233 新实现约第 221 行）；`PerParam.nCustid` → `GetValue("custid", ...)` 同名。

## 4. 411827：文档正确，代码确有缺口

证据链（旧系统）：
```
lbmdll/lbm_of/LBMExport.cpp:9207  ofStrategyQryFundidJJTG(char *pCA)
                          :9215  GETVALUE_GENPARAM
lbmdll/lbm_of/ofTrd.cpp:4625     COf::ofStrategyQryFundidJJTG(...)
                    :4640        GF_ChkOperQuery(BusParam.GenParam, stOperinfo)   ← 真的用了
lbmdll/GeneralBus/GeneralBus.cpp:21837  CGeneralBus::GF_ChkOperQuery(...)
                               :21864    exec sql..up_com_chkoper           ← 存储过程做柜员权限校验
```
`up_com_chkoper` 入参：`nServerid / nOperid / sOperpwd / cOperway / sOperwayExt / nFuncid / sStationaddr`。

字段对照（旧 g_ → 新框架）：

| 旧系统 | 新框架 | 状态 |
|---|---|---|
| `g_funcid` | `funcid` | ✅ 已有 fallback |
| `g_operway` / `g_stationaddr` / `g_userinfo` / `g_operwayext` | `operway` / `netaddr` / `userinfo` / `operwayext` | ⚠️ 名字不匹配，若调用方发 g_ 则收不到 |
| `g_serverid` | 无对应字段 | ❌ |
| `g_operid` | `custid`（客户代码） | ❌ 语义不同 |
| `g_operpwd` | `trdpwd`（交易密码） | ❌ 语义不同 |

即 **1 项对齐 / 4 项名字不匹配 / 3 项无对应落地字段**。更关键：新框架虽调了 `GetGeneralParam()`，但 `m_QryGeneralParam` 在整个业务中**一次都没被读过**，`ChkOper`/`up_com_chkoper` 出现 **0 次** —— 即新框架 411827 **完全没有柜员权限校验**，而旧系统有。

## 5. 判断修正：新框架对这类查询接口本就不做柜员校验

`CheckOperRight()` 在新框架只存在于各业务类，基类 `query_base.h` 无此方法：

```
lbm/lbm_otc_query/src/query_ret_cust_fund_asset_classify_new_business_811528.cpp:233
int CQueryRetCustFundAssetClassifyNewBusiness::CheckOperRight()
{ return 0; }                                  // ← 空桩
lbm/lbm_otc_query/src/query_otc_cust_a_fund_asset_business_831509.cpp:169
lbm/lbm_otc_query/src/query_ret_cust_a_fund_asset_business_811509.cpp:164
```

811528（410233 的姊妹接口）在 `Execute` 里调用 `CheckOperRight()` 但实现是空桩。**说明框架层对这类查询本就不做柜员权限校验，设计上应交给网关 KGMS 承担**；411827 的「缺失」更像框架既有取舍，风险等级由「单个业务漏项」下调为「需确认网关是否兜住」。

## 6. 待确认事项与建议处置（未经用户拍板不要自行实现）

| # | 待确认 | 影响 |
|---|---|---|
| 1 | 调用方实际按 `g_operid` 还是 `operid` 上送 | 决定要不要补 g_ 兜底 |
| 2 | 网关 KGMS 是否已做柜员权限校验 | 决定要不要补业务校验 |
| 3 | 若补，补在单业务还是查询基类统一 | 决定改动范围 |

建议分三步、风险由低到高：① 先改 410233 参数对比文档 1.1（纯文档，纠正自引入错误）；② 给 `CQueryBase::GetGeneralParam()` 补 `g_operway`/`g_stationaddr`/`g_userinfo`/`g_operwayext` 四条兜底（纯增量、不改现有行为）；③ 柜员校验是否补，**必须由用户或调用方拍板**，不应自行决定。

## 7. 可复用教训

1. 写参数对比「1.1 旧系统公共参数」前，**必须打开旧系统对应 `LBMExport.cpp` 确认是 `GETVALUE_PERPARAM` 还是 `GETVALUE_GENPARAM`**，再决定字段表是否带 g_。接口号前缀只能作为初判（4 开头→PERPARAM、7 开头→GENPARAM），仍需逐接口实证。
2. **不要以新框架代码注释为准**：411827 新实现注释写着「老系统 GETVALUE_PERPARAM 口径」，实测旧系统是 GENPARAM。
3. **mock 用例通过不等于生产参数对齐**：`req_70411827.xml` 实际只发了 `custid / g_funcid / orgid / tacode`，1/1 PASS 无法证明 `g_operid` 那一套在生产可用。
4. 判断「新框架漏实现」前，先查同类姊妹接口是否同样是空桩/轻量实现，避免把框架层设计取舍误报成个别业务缺陷。

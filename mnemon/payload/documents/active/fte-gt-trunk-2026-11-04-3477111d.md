# FTE 测试控制台（gt_trunk）本机部署与静默失败修复（2026-11-04）

范围：`gt_trunk/DYS-FRAMEWORK/fte/test_all/webui` 控制台在本机（`/home/lsz/code/work/gt_test`）的部署、
端到端联调、以及联调中暴露并修复的三类「任务成功但无数据」静默失败。
原始完整报告在仓库内：`DYS-FRAMEWORK/fte/doc/test/本机功能性能复测与控制台部署_20261104.md`；
当日工作日志 `work_log/20261104.md`；知识库 `study/knowledge_base_system/13_FTE测试控制台.md`（缺陷小节）、
`12_性能测试.md`（不绑核基线）。

## 1. 控制台结构与执行面

- 入口：`server.py`，默认 `http://0.0.0.0:8443/`；启动日志会打印 `work_root`、`python` 版本、`container=` 开关。
- 动作定义：`actions.py`。`action=all` 表示单市场「编译 → 部署 → 启动链路 → 功能 → 性能(capture) → 停止链路」，
  `market=all` 时对 sh/sz 各跑一遍；`action=allrun` 表示全局一键：**sz → sh 顺序**，每市场 启动 → 功能 → 性能 → 停止。
  编译步骤 `compile.sh -r`，部署 `compile.sh -r --deploy-only`，链路 `run/start_all.sh --local --market <m>`。
- 任务执行与归档：`jobs.py`（`plane.parse_reports_in_container` 统一解析）、`store.py`（JSON 落盘）。
- 容器执行面：`plane.py` 的 `exec_in_container`（支持注入 env），探针统一走 `plane.run_probe`。
- 报告解析：`parsers/func_report.py`、`parsers/perf_report.py`；单次解析可用 `parse_cli.py` 直接验证。

## 2. 三个部署即暴露的静默缺陷（本次核心收获）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| ① | `/api/link` 的进程 PID 显示成 `ATP_RES_ROOT: /mnt/work/...\n232` | 容器 `/etc/profile` 会打印横幅，登录 shell（`bash -lc`）stdout 被污染 | 探测类命令改用**非登录 shell**（`plane.run_probe`），结果统一取 `last_line()`；`server.py`/`diagnose.py` 同步改用 |
| ② | 任务状态 success，但 `func/`、`perf/` 目录永远为空、页面无数据 | 两层叠加：`_has_py37` 判据被横幅污染 → 恒真 → 去调不存在的 `python3.7`；容器 locale 为 **ASCII** → 中文报告按 ascii 解码（或 `parse_report` 静默返回 None） | 判据改为 `last_line().startswith("/")`；所有文本 IO 显式 `encoding="utf-8"`（含 `errors="replace"` 的读）；`docker exec` 注入 `PYTHONIOENCODING/LANG/LC_ALL` |
| ③ | 手册称「功能/性能测试会自动起链路」 | 门禁在**提交阶段**就校验链路状态，未启动直接 409 | 按实测修正 `MANUAL.md`：必须先点该市场「启动链路」 |

排查手法（可复用）：
- `parse_report(path)` 在 `cwd=/` 返回 None、在 `cwd=webui` 返回 ok，说明是环境（sys.path/locale）而非数据问题；
- 容器内 `python -c` 打印中文即报 `UnicodeEncodeError: 'ascii' codec ...`，且 `locale.getpreferredencoding()` 为 `ANSI_X3.4-1968` → 用 `PYTHONIOENCODING=utf-8` 重跑即恢复；
- 直接 `grep -n 'open('` 全量排查 webui 的文本 IO，逐处确认是否显式编码（`store.py` 的写路径同样需要）。

修复后验收：`func/summary.json`、`perf/summary.json` 正常落盘，日志出现
`--- 功能测试归档：8 用例，通过 8，失败 0`；页面 `/api/runs/<id>/cases|perf` 与归档逐项一致。

## 3. 归档与查询接口

- 归档路径：`/home/lsz/code/work/gt_test/webui_results/YYYYMMDD/<run_id>/{func,perf}/summary.json`，
  run_id 形如 `20261104_101706_allrun_all`、`20261104_101142_func_sz`、`20261104_101232_capture_sz`。
- 页面数据源：`/api/runs`、`/api/runs/<id>/cases`、`/api/runs/<id>/perf`、`/api/link`、功能日历/功能树接口。
- 功能树按「市场 → 业务（etf/spot/fill）→ suite」聚合 totals；性能趋势取最近 `capture` 轮次的 summary。

## 4. 本机实测（2026-11-04，单机 16 核，未隔核、未绑核）

| 项 | 结果 |
|---|---|
| 深圳功能 | 8/8（CLI 直跑与控制台一致，35.4s） |
| 上海功能 | 12/13（70.4s）；唯一失败为 `spot` 的 `FTE 撤单测试`，属已知用例串扰，非回归 |
| 深圳性能（独立 capture，含 30s 预热） | P50 10.57 µs |
| 上海性能（同上） | P50 18.23 µs；抓包 8988 匹配、outlier 32 |
| 全局 allrun（**无预热**） | 深 11.04 µs / 沪 23.50 µs |
| 编译耗时 | 全量 290.7s / 397.8s / 441.2s 三次；部署 2.4s；启动 5.1–7.2s；停止 3.1–4.1s |

结论要点：
- 深市 P50 在不绑核条件下稳定在 10.4–10.7 µs，与远程（10.3–10.7）及另一台机（12.2）同量级 → 深市链路对绑核不敏感；
- 沪市约为深市两倍且长尾重，归因于 16 核共享 + 3 个 SSESTEP 写库线程 + 无隔离（`step_poll_sleep_us=500` 已生效）；
- **报数纪律**：只引用独立「性能测试」轮次（含 30s 预热），不得与 allrun（无预热）混比；outlier>5% 时须 `--trace` 复算未过滤中位数，P50 不得单报。

## 5. 已知限制与坑

- gdb 热点采样在容器内取不到有效栈（权限不足），页面热点区显示「未采集」，不影响功能/性能指标。
- 容器内 Python 为 **3.6.7**（无 `python3.7`），宿主机 3.10/3.12；控制台代码只用标准库。
- 编译会重生成 6 个 codec 相关文件（`messages_agw_external.*` 等），提交前需回退，避免污染业务改动。
- 复测/重启控制台：先 `pkill` 旧进程再启动，最后 `health=200` + 4 页 4 静态资源 200 作为验收。
- 各动作都有超时（build 2400s / func 600s / capture 300s / start 180s / stop 120s），观测时以 steps 输出为准。

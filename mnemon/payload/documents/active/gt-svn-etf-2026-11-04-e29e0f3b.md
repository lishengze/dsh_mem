# gt_svn 沪市/深市 ETF 复测修复（2026-11-04）：数量单位真因与发送链路三层缺失

承接文档 `9e861d20-7da8-4980-a9c5-34e5fcbae404`（11-03 结论：ETF msgid 1010/1007 被 FTE 拒绝、性能样本恒 341）。
本文记录 11-04 这一轮**已用实验证实**的两条结论，供后续接手者复用，避免重跑。
源码工作副本 `/mnt/work/gt_svn`；构建目录 `/mnt/work/gt_svn/DYS-FRAMEWORK/fte_all/build_root/build_release/gw_api_boost/ute_api/`。
汇报文档：`svn_work/46_沪市与深市ETF修复记录_20261104.md`，提交 `f8749fbe8`（仅测试用例与文档）。

## 1. 沪市 2/5 → 4/5：真因是数量单位，不是账号配置

FTE debug 日志给出精确证据：

```
CheckQtyStall 3417 | Qty buy stall error, order_qty=[100], qty_unit=[10000].
```

代码逻辑：`IsFixed(order_type)` 为真时取 `buy_qty_unit`，否则取 `market_buy_qty_unit`。

| 参数文件 | BuyQtyUnit |
|---|---|
| `cash_auction_params.xml`（**FTE 实际加载**） | 10000 |
| `cash_auction_params_ute.xml` | 100 |

用例下单 100 → `100 % 10000 != 0` → 拒绝码 10。gt_trunk 同名文件同样是 10000，所以这是**用例与上场数据不匹配**，不是代码缺陷，也没有账号维度问题。

处置：`order_qty` 100 → 10000，并同步 `order_rtn_buy` / `trade_rtn_buy` / `cancel_rsp` 三份期望值、`exec_type` → 1。
结果：委托买入 PASS、成交回报校验 PASS；**撤单仍失败**（用例间串扰，远程环境同样存在，未修）。

## 2. 深市 ETF：发送链路三层缺失（按 gt_trunk 方案补齐）

gt_svn 的新代 API 对 ETF **完全没有支持**，且是三层叠加，逐层验证：

| 层 | 缺失点 | 现象 / 证据 |
|---|---|---|
| ① | `UTEClientHandlerImpl::SendMessage` 没有 ETF case | 落到 default 分支，打印一条 warning 后 return（`api/src/ute_client_handler_impl.cpp`） |
| ② | `AgwClientImpl::SendMessage` 的**直连分支**白名单只有 `kAgwMsgCashAuctionOrder` / `kAgwMsgCancelOrder` | ETF 被静默丢弃，**这是最后一环**；网关登录分支另有同构白名单 |
| ③ | `process_etf_order` 实现不存在 | gt_svn 该文件 2178 行 vs gt_trunk 3538 行；除函数本体外还缺 FTE 侧符号 `SHOrderType`/`SZOrderType`/`kPktETFReq`/端点与日志成员 |

补齐后的效果对比：

| 阶段 | 深市 ETF 用例 |
|---|---|
| 修复前 | 等待回报超时，FTE 侧零报文 |
| 补齐 ①③ | 仍无报文（说明还有 ②） |
| 再加 ② | **50ms 收到委托回报**，从"没反应"变为"能收到" |

**未解决**：收到回报但 3 个字段不匹配，以及 ETF 用例跑完后心跳超时。
字段差异：`business_type` 期望 12 实际 1；`cust_id` 期望 `03000028048439` 实际 `1000000000000001`；`price` 期望 10000 实际 0。
初步判断：`business_type=1` 说明 ETF 可能仍按现货分支处理（报文号或分发层未对齐）；`price=0` 属 ETF 市价申购无价；`cust_id` 是期望值写用例值、FTE 回资金表值。

## 3. 副作用与未收敛点（务必先确认再继续）

- 路由补丁一度导致深市 `fte_combo` 从 2/4 掉到 1/4，随即回退。回退后仍能收到委托回报，之后又出现"ETF 跑完心跳超时"（`fte_combo` 1/4，心跳用例 35000ms 超时）。
  => 最终有效的路由补丁形态在本次记录中**不确定**（`AgwClientImpl::SendMessage` 有网关登录与直连两个分支，`ute_switch=1` 走直连），继续前先确认当前工作副本里到底补了哪几处、以及心跳超时是新引入还是既有问题。

## 4. 两个值得记住的坑

| 坑 | 说明 |
|---|---|
| 补丁打到错的分支 | `AgwClientImpl::SendMessage` 有两处同构白名单；用 `str.replace(..., 1)` 只命中第一处（网关登录分支），直连分支没改到，白跑一轮。改这类文件后应 grep 确认"剩余匹配数" |
| 部署库路径 | `libagw_ute_api.so` 在 `gw_api_boost/ute_api/`，**不是** `api_fte/`；第一次 `cp` 失败导致客户端仍用旧库、结论失真。部署后必须比对 md5 |
| 命名空间 | 新增成员函数若追加到文件末尾，可能落到 `namespace uteapi/agw` 之外，报 `MsgTypeNo_def/kPktETFReq/endpoint_/on_log 未声明`；函数必须插在命名空间内、紧跟同类函数之后 |
| 僵尸进程 | 复测前检查 `Z` 状态进程；重启需先 `export WORK_ROOT`，端口占用：33002 (ute)、39142 (mock_exch_server)、39144 (mock_sqlserver) |

## 5. 下一步（按优先级）

1. 确认 `business_type` 为何为 1：ETF 报文是否真的进了 `DealTradeETFOrderReq`，还是仍走现货分发。
2. 定位 ETF 下单后心跳超时：连接是否被对端关闭、ETF 分支内是否有异常。
3. （可选）撤单串扰按 `client_seq_id` 过滤。

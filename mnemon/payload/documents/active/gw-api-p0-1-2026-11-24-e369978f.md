## 1. 注释粒度：用户收窄为「只有一处」

先按“全采上游 + 注释全部热路径日志”执行了一轮，注释了 `SendMessage` 内 40/41 行、随后又补注释 `DispatchMessage` 19 处等（两树合计 68/69 行 `[性能]`）。用户随即否决：

> 日志需要注释的就一处，不是全部都需要注释的，只注释之前性能优化分析时，确定的那一处会导致上行延时变高的日志。

于是**两次恢复到上游原样**重做。最终只注释一处，两树各 8 行：

| 树 | 位置 | 内容 |
|---|---|---|
| boost | `agw_client_impl.cpp` L1134~L1141 | `SendMessage` 入口的 `std::ostringstream os; os << "SendMessage: status = [...] ngtp_revert/spec_query/ute_switch"` + `OnLog(kInfoLog)` |
| no_boost | 同文件 L1143~L1150 | 同上 |

关键细节：

- 注释范围是**整个 `if (client_handler_ != nullptr) { ... }` 的内层块**（`ostringstream` 构造 + 字符串拼接 + `OnLog`），因为耗时来自**字符串构造本身**，只注释 `OnLog` 一行等于没优化。
- 外层 `if` 与 `{}` 必须保留，否则 `else` 分支挂空、语法破坏。
- 其余 43/44 处 info/debug 日志**保持上游原样**，不再批量关闭。`DispatchMessage` 曾被按“每笔回报都经过即热路径”推定为热路径并注释，同样被推翻——判据是**性能分析已经把上行延时归因到的那一处**，而非结构上的调用频度推理。
- 改用状态机（先去注释、去字符串字面量）统计大小括号平衡：boost 496/496、no_boost 497/497，避免被注释里残留的 `/*`、`*/` 误导。

## 3. P0-1 补丁的两块内容与判据

1. 去掉 UTE 直连段外层 `/* */`，就地加警示注释（说明为何不能注释掉）。
2. `ute_client_.Connect(...)` 之后**早返回 `kSuccess`**，返回前补齐 `user_` / `password_` / `guomi_password_` / `user_type_`，但**不搬** AGW 路径的 `kUserPwdError` / `kLocationsError` 校验（否则 UTE 直连配置会被 AGW 侧 password 长度等约束拦住）。

判据串计数：`不可注释掉`（警示注释）与 `UTE 直连模式下已发起连接`（早返回块）**平时各 1、提交前各 0、提交后回到 1**；`[性能]` 行始终 8。

## 4. 编译前守卫：纯上游版本会被拒绝编译（有力旁证）

直接编译纯上游版本时被仓库的“UTE 直连块检查”守卫拦下：

- `活代码中的 ute_client_.Connect( 处数 = 1（原始文本 2 处）`
- `[FAIL] 第 1 个 Connect 重载（第 1990 行起）没有活代码的 ute_client_.Connect(`
- 后果描述：编译不报错，但运行时 `ute_client_.Connect()` 永不执行 → `Connect 返回 kLocationsError，等待 UTE 登录` → 15 秒超时，UTE 侧日志毫无连接记录。

即：**P0-1 是本地可编译的必要条件**，不是可选优化。应用补丁后守卫通过。

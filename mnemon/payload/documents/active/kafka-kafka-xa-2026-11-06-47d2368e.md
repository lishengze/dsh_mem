# 外部/远程 Kafka 接入与鉴权可配性（2026-11-06 实测）

ts: 2026-11-06；项目：otc_src（kgbp / libkafka_xa / kafka_record 记录推送）

## 背景
记录级 Kafka 推送走 `libkafka_xa.so`（XA 插件）。需要回答：能否直连**非本机**的外部 Kafka 组件，以及 broker 开启 SASL/SSL 时能否通过 `xaopen` 配置。

topic 名称、XA 命名与 kafka_xa / HCS 双通道分工见既有文档 `80ee5b2f-0239-4350-99fe-706465a22fcc`（`documents/active/kafka-10-11-12-topic-hcs-2026-11-06-80ee5b2f.md`）。本文只补充远程接入与鉴权结论。

## 1. 可直达外部 Kafka，改一行即可
`libkafka_xa.so` 内部**静态链接 librdkafka**，通过标准 TCP 直连 broker；`ldd` 无 librdkafka 外部依赖、`strings` 中约 15 处 `rd_kafka_*` 符号。因此 `127.0.0.1:9092` 只是示例值，改为远端地址即可，转发器代码无需改动。

`otcsrc/kgbp_x64_linux/conf/kgbp.xml`：

```xml
<!-- 单 broker -->
xaopen="topic_name=kafka_record;timeout=10000;bootstrap.servers=10.1.2.3:9092;async_call=yes"

<!-- 多 broker（逗号分隔，故障切换）-->
xaopen="topic_name=kafka_record;timeout=10000;bootstrap.servers=10.1.2.3:9092,10.1.2.4:9092,10.1.2.5:9092;async_call=yes"
```

改完**重启 kgbp**。`conf/kafka_forward.json` 的 `"xa"` 不变——那是 XA 名，不是地址（同仓库内 `kafka_xa` 已用逗号分隔多 broker 的写法，可作参照）。

## 2. 跨服务器必须同时确认的 5 项（含最常见的坑）
| 项 | 要求 | 不满足的现象 |
|---|---|---|
| 网络 | kgbp 主机可连 broker 9092 | 连不上、消息积压 |
| `advertised.listeners` | broker 对外通告地址必须是 kgbp 可达的 | **最常见**：bootstrap 能连，但元数据返回 `localhost`/内网主机名，后续发送全部失败 |
| topic 预建 | 外部 broker 常关闭 `auto.create.topics.enable` | 报 topic 不存在 |
| 鉴权/加密 | broker 若启 SASL/SSL | 见第 3 节，**未验证** |
| 超时 | 跨机房应加大 `timeout`（现 10000ms） | 高延迟下偶发超时 |

连通性自测（无需装客户端）：
```bash
bash -c "cat < /dev/null > /dev/tcp/10.1.2.3/9092" && echo 通 || echo 不通
```
预建 topic：
```bash
kafka-topics.sh --bootstrap-server 10.1.2.3:9092 \
  --create --topic kafka_record --partitions 3 --replication-factor 2
```
验证真到远端：在 broker 机器 `kafka-console-consumer.sh --bootstrap-server ... --topic kafka_record --from-beginning --max-messages 3`，或改 `task/kafka/show_evidence.py` 的 `BOOTSTRAP` 后运行。

## 3. 鉴权可配性：未证实，不得假定可用
- 库内可见 `security.protocol` / `sasl.mechanism` / `sasl.username` / `ssl.ca.location` / `ssl.endpoint.identification.algorithm` 等字符串，但那是**内嵌 librdkafka 自带配置表**，不代表 XA 会透传。
- 仓库**无 `libkafka_xa` 参数文档**（`xa/` 目录仅二进制；`xaopen`/`topic_name` 的检索只命中其它 XA 的用法）。
- 决定性实验：向 `xaopen` 注入非法值 `security.protocol=BOGUS_VALUE` → kgbp 正常启动、999997 用例 `pass=1`、钩子无 `forward failed`、日志**没有** librdkafka 的 "Invalid value for configuration property" 报错。注入非法属性后 kgbp 仍能启动说明 XA 是惰性初始化。
- 结论：`xaopen` **不是 librdkafka 全属性透传**（也可能"透传但失败被静默忽略"，两者从日志无法区分）。若外部 broker 强制 SASL/SSL，**先做受控验证**，或改用网络层白名单/内网直连。
- 实验后已还原配置（`BOGUS` 残留 0，md5 复原），kgbp 重启正常（4 进程、`[SUCCESS] KGBP 服务启动成功`）。

## 4. 与本地 Kafka 并存
不要改现有 XA；**新增**一个不同 name / 不同地址与 topic 的 XA，把 `kafka_forward.json` 的 `"xa"` 指向新 XA，既有链路不受影响。

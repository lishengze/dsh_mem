## 3. 核对命令被实跑证伪的四个坑

文档里的核对命令一律**先实跑、再写进文档**，本轮因此改掉 4 处：

1. **`$"\r"` 不是 ANSI-C 转义**。它是本地化字符串，退化成匹配字母 `r`，导致 2340 行全中（假阳性）。正确写法 `$'\r'`，实测结果 0，与 `file` 判断一致。
2. **嵌套引号太绕**。原写法用 `docker exec ... bash -c '...'` 套多层转义，极易出错；改为「先 `docker exec -it otc bash` 进容器，再逐条执行」，可读且无转义陷阱。
3. **整树 `svn status` 会报 `E000022`**：`Common/tools/msg_sender/msg_sender_release/Release` 下有非 UTF-8 文件名（`afadmin?…沟通工作文档.docx` 一类）。报错**不影响** `svn status | grep -E "^M"` 的结果，属已知问题；也可改为只查目标目录：`svn status api/gw_api_boost/api/src fte/include/tech/network | head`。
4. **恢复命令不能用通配 sed**：`tcp_endpoint.h` 的 L749 还留着一份**旧的注释副本**（`// static const bool hb_legacy_reset = ...`），通配 sed 会一起放开 → 变量重复声明 → 编译失败。sed 的 `\` 续行写法在 `-e` 里也不合法（`unterminated address regex`）。可靠做法是**按行号的两条独立 sed**。

## 5. 为何 `git diff` 与 `svn diff` 范围不一致

SVN 工作副本基线**落后**于 git trunk，所以同一文件在两侧的改动范围不同：`git diff` 只显示 2 行（`tcp_endpoint.h` 的回退开关注释化），`svn diff` 显示 4 个 hunk（含 `#include <cstdlib>`、`<boost/date_time/posix_time/posix_time.hpp>` 等基线差异）。

结论：**以 `svn diff` 为准判断将提交什么**，不要用 `git diff` 推断 SVN 提交内容；反之核对"是否改动了工作副本"时可用 `git diff` 定位。

## 2. 读 `/proc/<pid>/stat` 的字段陷阱（可复用教训）

`/proc/PID/stat` 的第 2 个字段是 `comm`（形如 `(urc)`），进程名含空格会让 `awk '{print $14+$15}'` 整体错位，得到恒定值 → 误判「ticks 全等」。

正确读法（不依赖字段计数）：
```python
st = open('/proc/%d/task/%s/stat' % (pid, tid)).read().split()
ticks = int(st[13]) + int(st[14])
```
判据：**任何按 ticks 排序做绑核的脚本，先验证 ticks 有区分度**；验证手段必须是 Python `split()` 或 `comm` 剔除后的解析，不能用 `awk` 裸字段。

## 3. 三个真实环境差异（复现 195 号 23.5 µs 的钥匙）

1. **mock 位置（最关键）**：195 号 121 本地 `127.0.0.1:9000/9001` → 23,520 ns；现环境 mock 在 42 → 42,770 ns。配置差在 `urc_cfg.xml`（`bak_39143` 为 127.0.0.1，当前为 `10.189.111.42`）。
   机理：mock 在 42 时 RTT 0.487 ms，回报延迟数百 µs 回来，队列持续有消息；mock 在本地时回报 <10 µs 返回，委托与回报几乎同时到达，队列排空即自旋。
2. **完整链路**：api(42) → FTE(49:33002) → URC(121:39142) → mock。压测客户端 `mock_client` 是 **UTE 直连模式**，连的是 FTE 不是 URC（`sz.json` 的 `ute_server_ip=10.189.111.49` / `33002`）。
3. **FTE 占网关**：URC 网关一口一连，FTE 先连上后 42 的压测客户端连不进来；现象是 `121:39142` 只有 FTE 一个连接、`mock_client` 全在 CLOSE-WAIT、回报匹配 0%。

本地 mock 复现（42 样本，同机对比）：T2-1→T2-2 **21,460 → 290 ns（-98.6%）**；端到端 31,620 → **12,720 ns**。

- **反证不同源**：`exch_business_manager.cpp:155 DealMsgHandle()` 空队列走 `sleep_for(200µs)` 再 `continue`，且每次只 `Pop` 一条；这条路径的「队列等待」应在 0~200 µs 量级，与 218 §6 的 21 µs、§4 的 100 ns 都不符 ⇒ **被测二进制与这份源码不同源**。因此实验顺序把「核二进制/构建来源」排在第一位。

- 结论排序据此调整：**队列占用/背压升为首因，跨核放置降为「非决定因素」**。

# API 热路径优化（日志门控 + 心跳定时器自续期）与两个联通性缺陷

面向 gt_trunk 中 boost / no_boost 两棵 API 树的优化与缺陷记录。核心结论：**"注释掉 `write()` 里的定时器重装"不是一个孤立改动，它强制要求在 `register_send_timer()` 的回调里补上自续期，否则空闲约 20s 必断链。**

## 1. 两项优化与实测收益（单实例 P50，同一二进制可复现）

| 项 | 做法 | 收益 |
|---|---|---|
| 热路径日志 | `SendMessage` 内 `ostringstream` + `OnLog` 改为 env 门控（`AGW_SM_TRACE`）/ 注释 | **-901 ns/笔** |
| 委托后定时器 | `write()` 成功后不再无条件 `register_send_timer()` | **-1996 ns/笔（约 -2.0 us）** |

三档对照（各 3 轮中位）：完全未优化 **6692 ns** → 仅关热路径日志 **5791 ns** → 全优化 **3795 ns**，合计 **-2897 ns（-43%）**。心跳定时器是两项里更大的一项。

热路径日志的代价构成：heap 分配 ×2（`ostringstream` 缓冲 + `str()`）+ 4 次格式化 + 日志回调。boost 版 12 处、no_boost 版 28 处。

## 2. 关键机制：为什么"去掉重装"必须配套自续期

1. **asio 定时器是一次性的**：`expires_from_now()` + `async_wait()` 只触发一次，不会自循环。
2. **优化前的"反复注册"由业务流量隐式提供**：每笔委托 `write()` 成功都重装一次。因此该缺陷**压测时不暴露，只在空闲时暴露**——这是它最容易漏掉的原因。
3. 去掉重装后，建链时那次注册（`tcp_endpoint.h` L338 附近，构造函数/建链路径）成为全程唯一一次 → 发完 1 次心跳后再无定时器。
4. 对端 `detect_timer` 阈值是 **`period × 2`**（`detect_timer_.expires_from_now(hb_hd_->get_period_milli() * 2)`，本环境 10s 周期 → 20s）→ 判 `kHeartbeatTimeout` → `do_close` 断链。

**表现最坑**：委托能正常发出（`write()` 不受影响），但空闲约 20s 后连接被对端断开，看起来像网络抖动。

### 必须补的那一处

`DYS-FRAMEWORK/fte/include/tech/network/tcp_endpoint.h`，`register_send_timer()` 的 `async_wait` 回调内（约 L843）：

```cpp
if (!ec) {
    this->hb_hd_->send_hb_message(this);
    if (socket_.is_open() && !has_been_closed_) {
        register_send_timer();   // ★ 自续期：按同一周期立即再注册
    }
}
```

- 必须判 `has_been_closed_`：`do_close()` 先置 `has_been_closed_ = true` 再 `cancel()`（`send_timer_` / `detect_timer_`），但回调可能已入队/在飞行中；不判就会为已关闭/已销毁的连接再注册 → 悬挂定时器。
- `write()` 里原来的重装已改为 `if (UNLIKELY(hb_legacy_reset)) register_send_timer();`，保留 **`HB_LEGACY_RESET=1`** 回退开关，用于**同一二进制**做 A/B，保证性能结论可复现。
- **实施顺序**：先加自续期、再注释 `write()` 里的重装。反过来会出现"跑 20s 就断链"的中间态。

### 实测证据（真机日志）

`send_hb_message` 78 次，间隔 10.0s，持续约 10 分钟（04:12:28 → 04:22:30）→ 自续期确实生效，无需依赖业务流量维持心跳。

### 计时口径上的坑

`register_send_timer()` **函数体本身只有几十纳秒**（≈2 次 asio 接口调用），但真正的时间花在它触发的副作用上：`expires_from_now()` → 内核 `timerfd_settime`（0.410 us）、`async_wait()` → `epoll_ctl`（1.068 us）、定时器队列锁 + 被取消回调 post + io 线程唤醒（≈0.717 us）。所以"省 1.9~2.2 us"与"函数体几十纳秒"并不矛盾——省的是 2 次系统调用 + 锁 + 跨线程唤醒。

## 3. 两个联通性 bug（直连模式）

| bug | 位置 | 因果链 |
|---|---|---|
| ① 直连建立段被 `/* */` 整块包住 | `agw_client_impl.cpp` 约 L2091~L2160 | 合并线上代码时被注释。线上走 AGW 网关不需要，但本仓测试用 UTE 直连（`ute_switch=1`）必须保留；不修则 `ute_client_.Connect()` 从不被调用 → **连接根本不发起**，UTE 侧零日志 |
| ② `sendlogin()` 被注释 | `ute_client_handler_impl.cpp` 约 L140（boost 树仍为注释态，no_boost 树为活代码） | 直连模式下它是**唯一**发 1001 的地方。不修则无 `LogOnAns` → `status_` 停在 `kStatusConnected` → 后续委托在 `SendMessage` 落进 `set_cust_info()`（只认 800005 `AgwMsgCustLoginReq`）→ cast 失败 → `kSetCustInfoError` → **报文一次都不下发** |

### ① 的配套必要改动（易漏）

- 去掉 `/* */` 后必须在 `ute_client_.Connect()` 之后**早返回 `kSuccess`**；否则继续走 AGW 路径，因 UTE 直连的 `connection/*.json` 里 `locations=[]` 而返回 `kLocationsError`。
- 早返回前必须补齐 `user_ / password_ / guomi_password_ / user_type_`，否则回切路径的报文会静默带空账号。
- 早返回时**不要搬运** AGW 路径的 `kUserPwdError` / `kLocationsError` 校验。

## 4. 顺带发现的维护不一致：`AGW_SM_TRACE` 两棵树语义不同

| 树 | 状态 |
|---|---|
| boost | 12 处**全在注释里** → 运行时设环境变量**无效**，必须改代码重编 |
| no_boost | 28 处中 14 处是**活门控**（另 14 处注释态）→ 设环境变量即生效 |

排查时若按 no_boost 经验去 boost 树设 `AGW_SM_TRACE`，会误判"日志开关失效"。`[性能]` 标记在 boost 树共 30 行（L1129~L1572 一带，集中在 `SendMessage` 内）。

## 5. 复查方法（可复用）

文档级事实核对用"生成即校验"循环：行号逐条 grep 确认存在、关键数字与上游文档（125 号）逐值对齐、表格列数一致性检查、回调阈值与消息号链路（`set_cust_info` → `AgwMsgCustLoginReq` = 800005）读源码确认、日志证据复核。本轮 8 轮复查末轮零修改通过。
